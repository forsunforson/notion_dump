# 连接树莓派和Arduino
create_time: 2023-03-25T08:51:00.000Z
modify_time: 2025-04-27T06:42:00.000Z

作为实现iot系统的一个步骤，想法比较简单

主要利用了Arduino IDE提供的功能

在IDE里存在工具 `./hardware/tools/avr/bin/avrdude` 使用这个工具能够将二进制文件烧录到arduino中

arduino通过usb连接到树莓派，通过 `/dev/tty*`可以查到 基本上是`/dev/ttyACM0`

使用命令

```shell
./avrdude -C../etc/avrdude.conf -v -ptmega328p -carduino -P/dev/ttyACM0 -b115200 -D -Uflash:w:/home/pi/demo.hex:i
```

将二进制文件烧录到arduino uno中

解释下上述命令 -v 输出额外信息，方便debug -p 表示零件型号，可以网上查。对于arduino micro是`atmega32u4` -c 制定编程器，micro `avr109` -P 串口地址 -b 波特率 -D 禁止自动擦除山村空间 -U 存储类型，操作方式，hex文件名和类型

使用python-serial包，能够在树莓派上发送或者读取串口信息 树莓派

```python
import serials = serial.Serial('/dev/ttyACM0', 9600, timeout = 1)try:    while 1:        s.write('s')        response = s.readall()        print(response)except:    print('port close')    s.close()
```

Arduino

```c
void setup() {    Serial.begin(9600);}void loop() {    if (Serial.available() && 's' == Serial.read()) {        Serial.println("pong");    }}
```

现在发现一个新的工具Gort，使用Gort可以直接烧录arduino，扫描端口 这样就可以不用安装Arduino IDE了 可以写一个脚本实现自动安装

使用serial工具能够读取串口数据，但是读到的数据为二进制数据。 不能保证流的开端是否是正确的，结尾也不一定正确。 现在需要做的是，如何把第一个读取到的`/r/n`作为结尾，开始解析数据。 如果上一段的结尾还有未读完的byte，怎么和后面的拼接起来一起读。

Arduino传感器读到的是电压，uno板的值是10bit的取值范围0～1023，电压范围是0～5V。因此能够读到4.8mV的电压变动。但是电压和具体传感器的值的对应关系，还需要通过电路去计算。

疑问：ttyACM0作为一个类似于文件的伪终端，读写文件时是如何表现的？ >答案在于I/O阻塞。伪终端只能在其内核缓冲区内保存一定数量的数据，当该缓冲区满并且 yes 尝试调用 write(2)时，write(2)将被阻止，并将yes 进程移至可中断的睡眠状态，直到xterm能够读取缓冲中的字节。 >如果TTY连接到串行端口，也会发生同样的情况。假设 yes 能够以比9600波特的速率传输数据，但是如果串行端口被限制在低的多速度上，内核缓冲区很快就会被填满，并且任何后续的 write(2) 调用都会导致进程睡眠（或收到返回的错误号 EAGAIN ，如果进程要求非阻塞I/O的话）。 >如果我告诉过你，即使内核缓冲区中还有剩余空间，也可以主动地将TTY置于阻塞状态，更进一步的说，每个试图 write(2) 到TTY的进程都会自动阻塞。那么这种功能的用途是什么？ >假设我们正在以9600波特率的速度与一些旧的VT-100通信。我们刚刚发送了一个复杂的控制序列，要求终端滚动显示。此时，终端会因执行滚动操作无法以9600波特的全速率接收新数据。实际上，UART仍然以9600波特运行，但终端中没有足够的缓冲空间来保持接收字符。现在就是将TTY置于阻塞状态的好时机。但是，我们该如何从终端做到这一点？ >我们已经看到，TTY设备可以被配置为给某些数据字节特殊的处理。例如，在默认配置中，收到的 ^C 字节不会通过read(2)传递给应用程序，而是会将 SIGINT 信号传递到前台工作。类似地，可以将TTY配置为对停止流和开始流做出反应，通常分别是 ^S （ASCII码19）和 ^Q （ASCII码17）。旧的硬件终端会自动传输这些字节，并期望操作系统相应地调节其数据流。这被称为流控制，这就是为什么当你偶然按下 ^S 时，你的xterm 会“锁定”。 >这里有一个重要的区别：写入由于流控制而停止的TTY，或者由于缺少内核缓冲区空间，只会阻塞你的进程，而从后台工作中写入TTY将导致SIGTTOU 暂停整个进程组。我不知道为什么UNIX的设计师必须发明 SIGTTOU 和 SIGTTIN ，而不是仅仅依靠I/O阻塞，但我最好的猜测是负责工作控制的TTY驱动是为了监视和操纵整个工作——而不是其中的单个进程。

从这个说明看，如果ttyACM0的系统缓冲区满了，那么会停止写入。 但是如果串口仍不断写入，是否会发生数据丢失？
