# 程序员的进阶之路[2]

## 新手入门

If else

```java
private static String MAN = "man";
private static String WOMAN = "woman";
@Data
static class Person{
    private String gender;
    private String name;
}
public static void main(String[] args) {
    Person p = new Person();
    p.setGender(MAN);
    p.setName("张三");
    if(Objects.equals(p.getGender(),MAN)){
        System.out.println(p.getName() + "应该去男厕所");
    }
    if(Objects.equals(p.getGender(),WOMAN)){
        System.out.println(p.getName() + "应该去女厕所");
    }
}
//输出 ：张三应该去男厕所

```

## 老鸟报道

lambda策略模式

```java
private static Map<String, Consumer<String>> FUNC_MAP = new ConcurrentHashMap<>();
private static String MAN = "man";
private static String WOMAN = "woman";
static {
    FUNC_MAP.put(MAN,person ->{System.out.println(person + "应该去男厕所");});
    FUNC_MAP.put(WOMAN,person ->{System.out.println(person + "应该去女厕所");});
}
@Data
static class Person{
    private String gender;
    private String name;
}
public static void main(String[] args) {
    Person p = new Person();
    p.setGender(MAN);
    p.setName("张三");
    Person p2 = new Person();
    p2.setGender(WOMAN);
    p2.setName("张三他老婆");
    FUNC_MAP.get(p.getGender()).accept(p.name);
    FUNC_MAP.get(p2.getGender()).accept(p2.name);
}
//输出： //张三应该去男厕所 //张三他老婆应该去女厕所

```

## 大佬进阶

DDD+策略模式

```java
private static String MAN = "man";
private static String WOMAN = "woman";
@Data
static class Person{
    private String gender;
    private String name;
    private static Map<String, Consumer<String>> FUNC_MAP = new ConcurrentHashMap<>();
    static {
        FUNC_MAP.put(MAN,person ->{System.out.println(person + "应该去男厕所");});
        FUNC_MAP.put(WOMAN,person ->{System.out.println(person + "应该去女厕所");});
    }
    public void goToWC(){
        FUNC_MAP.get(gender).accept(name);
    }
}
static class PersonFactory{
    public static Person initPerson(String name ,String gender){
        Person p = new Person();
        p.setName(name);
        p.setGender(gender);
        return p;
    }
}
public static void main(String[] args) {
    Person p = PersonFactory.initPerson("张三",MAN);
    Person p2 = PersonFactory.initPerson("张三他老婆",WOMAN);
    p.goToWC();
    p2.goToWC();
}
//输出：
//张三应该去男厕所
//张三他老婆应该去女厕所

```

## 明日之星

Actor模型+DDD+策略模式+事件响应架构

```java
private static String MAN = "man";
private static String WOMAN = "woman";
private static String WC_EVENT= "想上厕所";

@Data
static class Person extends UntypedActor {
    private String gender;
    private String name;
    public static Props props(final String name,final String gender) {
        return Props.create(new Creator<Person>() {
            private static final long serialVersionUID = 1L;
            @Override
            public Person create() throws Exception {
                Person p = new Person();
                p.setGender(gender);
                p.setName(name);
                return p;
            }
        });
    }
    @Override
    public void onReceive(Object message) throws Throwable {
        Pair<String,ActorRef> m = (Pair<String,ActorRef>)message;
        System.out.println(name + m.getLeft());
        m.getRight().tell(this, ActorRef.noSender());
    }
}

@Data
static class Toilet extends UntypedActor {
    private static Map<String, Consumer<String>> FUNC_MAP = new ConcurrentHashMap<>();
    static {
        FUNC_MAP.put(MAN,person ->{System.out.println(person + "应该去男厕所");});
        FUNC_MAP.put(WOMAN,person ->{System.out.println(person + "应该去女厕所");});
    }
    public void wc(Person p ){
        FUNC_MAP.get(p.getGender()).accept(p.getName());
    }
    public static Props props() {
        return Props.create(Toilet.class);
    }
    @Override
    public void onReceive(Object message) throws Throwable {
        Person p = (Person) message;
        wc(p);
    }
}
public static void main(String[] args) {
    ActorSystem actorSystem = ActorSystem.create();
    ActorRef person = actorSystem.actorOf(Person.props("张三",MAN), "ZhangSan");
    ActorRef toilet = actorSystem.actorOf(Toilet.props(), "Toilet");
    Pair<String,ActorRef> message = Pair.of(WC_EVENT,toilet);
    person.tell(message,ActorRef.noSender());
}
//输出
//张三想上厕所
//张三应该去男厕所

```

# 什么是DDD

> Domain-driven design (DDD) is a software development philosophy centered around the domain, or sphere of knowledge, of those that use it. The approach enables the development of software that is focused on the complex requirements of those that need it and doesn’t waste effort on anything unneeded. The clients of domain-driven design are often enterprise-level businesses.[1]

领域驱动设计是一种围绕着如何使用领域或领域知识的软件开发哲学。这种方法能够让软件开发专注于实现需要的复杂需求，而不用浪费时间在不需要的其他事情上。DDD的客户通常是企业级应用。

# 为什么需要DDD

软件设计的目的[3]

> 通过组件化完成关注点分离从而降低局部复杂度

架构设计的目的[3]

> 从业务出发、面向业务变化是我们现代架构设计成功的关键。架构设计的核心实质是保证面对业务变化时我们能够有足够快的响应能力。

说人话就是，软件系统最终需要解决的是业务需求，软件设计的“分而治之”的思想映射至业务领域，也需要将业务问题“分而治之”

抽象[4]

> 使用抽象能够精简问题空间，而且问题越小越容易理解

依赖倒置原则[5]

> 高层模块不应该依赖低层模块，两者都应该依赖其抽象；抽象不应该依赖细节；细节应该依赖抽象。

映射到业务领域，上下游之间应该依赖于领域模型的定义，而不应该依赖于领域模型的实现

对于TikTok User Service而言，可以具象为

上下游应该依赖于IDL中领域模型的实现（User Service时期），而不是依赖于存储字段（Go User时期）

从软件设计和架构设计目的出发，DDD就是一个综合的解决方案

> DDD的核心诉求就是将业务架构映射到系统架构上，在响应业务变化调整业务架构时，也随之变化系统架构。而微服务追求业务层面的复用，设计出来的系统架构和业务一致；在技术架构上则系统模块之间充分解耦，可以自由地选择合适的技术架构，去中心化地治理技术和数据。[4]

# 怎么设计DDD

定义阶段

避免把解决方案当问题去定义，与领域专家（或者说业务方）沟通，沟通的过程中需要定义清楚通用语言[7]

> DDD作为一种架构方法，最大的突破应该说是非常明确地区分出了问题域和解决方案域。而认知问题这件事情绝对不是技术人员擅长的，从我们学习编程起，我们就被如设计模式（Design Pattern）这样的解决方案所包围。想当年我自己最得意的事情也是refactor to pattern，也是把解决方案当成了“终极问题”来追求。

> 通用语言是团队自己创建的公用语言，团队中同时包含领域专家和软件开发人员。

设计阶段

需要遵循“模型是用来交流的”的这一核心原则

> 反对BDUF，但需要在前期对核心模型进行分析和设计，如果核心模型变化剧烈，则要考虑是否业务发生了根本性变化，需要建立新的模型限制建模工作的范围，将其局限在分解出来的核心问题域内需要有核心团队守护核心领域模型，任何对核心模型的改动都能够通过这个核心团队来促进更大范围的交流和沟通

实现阶段

DDD和微服务的有机结合，允许领域服务能够采用多样的技术架构解决问题

例如[6]

- Layered Architecture（分层架构）如上图
- Hexagonal Architecture（六边形架构）以领域服务为核心，对外提供ports & adapters
- REST 基于HTTP协议定义的分布式系统架构
- CQRS（读写分离）
- Event Oriented Architecture（事件驱动架构）
- Actor Model reactive编程范式，actor是最小的计算单元

# 个人感受

最容易产生共鸣的方式，就是自己既是业务的需求方、又是架构的设计人、还是系统的实现者

在实践中感受是否DDD能够减少在迭代中的重构工作量

需求方

实现一个系统，用于管理证券账户

需要有用户、账户、证券、外汇等概念

常见的场景是，多个用户拥有同一个账户的一定份额，用户可以根据当前账户净值买入或者卖出账户份额，并且查询某一用户在所有账户中拥有的证券价值（以人名币计）

设计人

- 需求方存在多种查看信息方式（命令行、前端网页、微信服务号）的需求，但是受制于开发者的人力投入和技术，存在优先级
- 多种方式需要的信息格式不一，但是核心流程是一致的，采用六边形架构，将领域模型与方法置于核心位置，采用Adapter去实现各种展示渠道的适配
- 人力投入有限，需要优先实现功能，不进行过度的领域划分
- 依赖的免费数据源不稳定，经常需要变更
开发者

优势

1. 使用repository概念，将依赖进行抽象后，在后期从A股扩展到港股，再扩展到美股时，不用改动核心逻辑
1. 后期的适配工作方便，免费数据源从手工输入->Sina Open API->Futu Open API->Python package，只需关注于适配的开发
1. 利用充血模型，不会在过段时间重新看自己代码，忘记当时在想什么
劣势

1. 前期开发量更高，整个核心逻辑的定义-实现-可用，花费时间远超过简单实现
1. 核心模型虽然较稳定的，但仍根据不同的业务需求在迭代，迭代的过程并未减少开发需要的工作量
